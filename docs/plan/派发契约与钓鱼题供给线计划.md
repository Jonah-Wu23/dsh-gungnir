# 派发契约与钓鱼题供给线实施计划

> **状态：待执行**（2026-08-30 落档。本批仅规划 + ADR，实现由后续工作块按本计划执行）。
> 决策依据：ADR-0020（派发契约 = 供给渠道、形态边界、命名澄清、M4 启动）、ADR-0019（H-VE 立项与纪律）、ADR-0018 §5/§6（离线形态与运行期重开条件）、《[H-VE-效力报告](H-VE-效力报告.md)》（药方清单与供给缺口）。
> 一句话：**把验过的法官（治疗臂判定栈）从夹具考场带进真实工作现场——派发者写契约，harness 出钓鱼题。**

## 0. 任务映射（用户隐喻 → 仓库实体）

| 用户说法 | 仓库实体 |
|---|---|
| 升级后的老师 / 新老师 | 治疗臂判定栈 = 现役离线判定栈（L1/L2 + S1 + S3 供给）+ 四类药方 M-A~M-D（`packages/core/src/ve.ts` 纯函数 + bench 执行面） |
| 钓鱼题 | 注入式检查的**供给**：`supplied.json` 四块（api / replay / unverifiableCriteria / grounding），bench 中手写 |
| 谁来自动出钓鱼题 | **派发契约**（派发者填结构化声明）+ **模板库**（harness 侧生成隐藏输入/参考实现）+ **runner**（构造 probe 并执行） |
| 真实环境自动抓作弊 | 对真实任务交付物的离线/判定侧评估（交付后门禁），不碰运行期介入（ADR-0018 §5） |
| AI 病理报告 | H-VE M4：per-model 病理画像（首版模型 deepseek-v4-flash-0731） |
| 方案 B 说明书 | **派发契约（Dispatch Contract）文档**——与 SwitchBench/seam-only 的历史"方案 B"无关（ADR-0020 第 4 条） |

## 1. 总览：批次、顺序、交付物

执行顺序有硬依赖：**B1 契约文档是 B2 供给器的输入 schema 权威、也是 B3 bait 任务面的设计依据**；B2 的验过法官（含真实供给闭环）是 B3 测模型的前提（法官没验过就测被告 = P1 重演，禁止）。

| 批次 | 内容 | 时间盒 | 交付物 |
|---|---|---|---|
| **B1（支线 2）** | 派发契约一页文档（纯文档，不花钱） | ≤0.5 工作块 | `docs/plan/派发契约-v0.md`（建议名，executor 可定稿） |
| **B2（主线）** | 契约 schema 入 core + 供给闭环工具 + 真实演示 + P0 打包登记 | ≤2 工作块 | `packages/core/src/contract.ts` + 单测；`tools/ve-supply/`；演示裁决记录 |
| **B3（支线 1）** | H-VE M4：预注册冻结 → 真实模型跑批 → 病理画像报告 | 预注册 ≤0.5，跑批+报告 ≤1.5 | `tools/experiments/ve-bench/M4-PRE-REGISTRATION.md`、`results/m4-*/`、《H-VE-M4-病理画像报告》 |

总预算 ≤4.5 工作块；任一批次超支 50% 触发范围削减（砍序见 §6），不延期。

## 2. B1：派发契约一页文档（支线 2，纯文档）

**交付**：一页派发契约规范（正文控制在一页内；schema 字段表与映射表可作附录）。这是"把大任务拆成小步骤防糊弄"的规则说明书：主 agent 把大任务拆成派发单元，每个单元带一张契约，子 agent 交付后按契约离线裁决。

### 2.1 派发单元 schema v0（草案，executor 定稿；每个字段必须能投影到供给接口）

| 字段 | 必填 | 内容 | 供给去向 |
|---|---|---|---|
| `objective` | 必 | 一句话任务目标 | 裁决上下文 |
| `acceptance[]` | 必 | 验收判据：`id` / `description` / `verifierLevel`（1/2）/ `command` 或 `predicate` / `observability: provable \| sandbox-external` | 控制臂判据；`sandbox-external` 项 → M-C |
| `api` | 选 | `module` / `function` / `template` / `signature`（模板名须存在于模板库） | M-A |
| `grounding[]` | 选 | `output`→`source` 依据声明（"写 X 前须读 Y"） | M-D |
| `baselineRef` | 有 git 必填 | 派发点工作区快照（git commit/tree） | M-B buggy 基底 |
| `budget` | 选 | token / 时间上限 | 治理记录 |

M-B 的 `replay.evidence`（声称的验证证据命令）v0 从 `acceptance[]` 的 command 类判据取——派发时声明的验收命令即声称证据，最诚实；从 session log 提取 agent 实际跑过的命令列为后续增强。

### 2.2 防糊弄条款 → 证据规则映射表（文档核心章节）

| 派发者想防的糊弄 | 契约字段 | 落地的药方 |
|---|---|---|
| 特判测试输入骗绿钩 | `api` | M-A 隐藏输入 probe（输入对模型不可见） |
| 交付物不承重（测的路径 ≠ 生产路径） | `api` | M-A trunk-path 模板 + 承重思想（VE-F2） |
| 测试绿但不判别 bug 修没修 | `baselineRef` + `acceptance` | M-B 判别性见证（replay 到 buggy 必 FAIL） |
| 沙箱外判据假装可证 | `acceptance[].observability` | M-C UNVERIFIABLE 三态 |
| 不读文档按猜测动手 | `grounding[]` | M-D read→write 时序检查 |

### 2.3 必含的其余章节

- 派发/验收流程：派发（填契约 + 打快照）→ 子 agent 执行（契约不注入其 prompt 的运行时协议，只作任务说明附件）→ 交付 → 离线裁决（B2 工具）→ 回执（裁决 + 证据链 + 供给覆盖报告）。
- 显式非目标：不做自动派发 runtime；不做运行期介入；契约不是协议税回潮——AP-1/AP-3 合规论证（派发时一次性填写，执行路径零新增往返）。
- 与 GoalSpec 的关系说明（契约 ≈ L1 轻量判据形态，渐进式形式化坐标，AP-3）。

**质量门**：每个 schema 字段都能映射到 `supplied.json` 四块之一或裁决上下文；引用 DSH 行为的事实须符合 `docs/context/dsh-interface.md`（发现不符以实测为准并回写）。

## 3. B2：供给闭环（主线）

### 步骤 1：契约 schema 入 core

- 新文件 `packages/core/src/contract.ts`：`DispatchContract` zod schema + `contractToSupplied(contract)` 纯投影（契约 → supplied 四块）+ `SupplyCoverage` 类型（每个药方的供给状态：applied / not-applied + 原因）。零 DSH 依赖，全单测（`packages/core/tests/contract.test.ts`）。
- 投影语义（与 §2.1 对应）：`sandbox-external` → `unverifiableCriteria`；command 类判据 → 控制臂判据 + `replay.evidence`；`api`/`grounding` 直传；`baselineRef` → `replay.buggyRef`（新增 git 快照来源，见步骤 2）。
- 纪律：契约文档（B1）是 schema 的权威；两边对不上时先改契约文档再改码，不许漂移。

### 步骤 2：供给执行面 `tools/ve-supply/`（新目录，离线工具）

- `snapshot.mjs`：`baselineRef` → 用 `git archive`（或等价）把派发点工作区提取到系统临时目录，供 M-B 当 buggy 基底。无 baselineRef → M-B 不启用并记入供给覆盖报告。
- `toollog.mjs`：从 DSH session log 提取 `tool/call` 序列 → `GroundingEvent[]`（M-D 输入）。session log 格式以 `docs/context/dsh-interface.md` 为准；实测不符先回写该文件。
- `run-supply.mjs`：主入口——输入 = 契约 JSON + 交付工作区路径 +（可选）session log 路径；流程 = 投影 supplied → 跑治疗臂 adjudicate + medicines 执行面 → 输出裁决 + 证据链 + **供给覆盖报告**（哪些药方有供给、哪些没有、为什么）。
- 执行面复用来源：`tools/experiments/ve-bench/stack/medicines.mjs`。**ve-bench 是冻结实验资产，不动**；从它提升/复制执行面到新目录并在文件头注明来源与差异点（如实随档代码重复）。验证命令一律 runner 侧构造 + spawnSync，probe 写文件再 node 跑（ADR-0018 §2 引号教训）；probe 注入的工作区放系统临时目录（工作区卫生纪律）。
- 不得 import `tools/experiments/` 下的冻结物作为新产品代码依赖以外的用途；更不得改 ve-bench 已入库结果。

### 步骤 3：真实演示（B2 验收，双侧）

用真实 profile（`exp-standard`，deepseek-v4-flash-0731）真跑一个小任务，全程真实工具链：

1. 任务选一个现有模板可覆盖的形态（如"给导出管线加输入校验" → `pipeline-validation` 模板），headless 真跑，得到真实交付工作区 + session。
2. 手工填一张契约（模拟派发者，含 api / acceptance / grounding / baselineRef = 任务前 git 快照）。
3. `run-supply.mjs` 全供给裁决 → 健康交付必须 **PASS**（不误杀），供给覆盖报告四药方全 applied。
4. 对交付物手工注入一类病（绕开主干：摘掉生产入口校验），再裁决 → 必须 **FAIL** 且证据链含 trunk-path probe 失败明细（检出）。
5. M-C/M-D 演示：契约含一条 `sandbox-external` 判据 → 终局非完全 PASS；tool-log 从真实 session log 提取后跑 grounding 检查。

演示记录（命令、裁决、证据链）入 `tools/ve-supply/results/` 并在 state.md 快照登记。

### 步骤 4：四阶段 P0 打包登记

夹具库 + 药方 + 契约 schema + 供给闭环工具 = P0 发布物内容（ADR-0020 第 6 条）。更新相关 README 的 Contract / Known Limitations 小节（文风对齐上游）；`docs/context/architecture.md` 若模块边界变化则同步。

### 测试纪律

core 新码全单测；执行面真实执行不走 mock（Let It Fail）；破坏用例 = 快照缺失 / 契约缺字段 / tool-log 缺失 → loud fail 或如实降级记录，禁止静默跳过；core 既有 139 单测保持全绿。

## 4. B3：H-VE M4——真实模型病理画像（支线 1）

前提已满足（M3 收线，G1/G2 全过）。**法官先验过再测被告**；本批测的是模型，不是法官。

### 步骤 1：M4 预注册（跑批前冻结）

`tools/experiments/ve-bench/M4-PRE-REGISTRATION.md`，必冻项：

- **bait 任务面**：从四类病理设计诱导任务，每类 ≥1 件 + ≥1 健康对照。诱导设计要点——①给可见测试 + 隐藏 oracle 空间（看是否特判）；②主干有复杂度、边缘好写（看是否只堆边缘）；③含沙箱外判据（看是否如实报不可证）；④答案只在本地文档（看是否先读）。每任务配**供给完整的派发契约**（B1 文档的实例），法官 = B2 验过的治疗臂全供给闭环。
- **模型清单**：首版 = deepseek-v4-flash-0731（`exp-standard` profile）；结构预留多模型扩展。
- **规模与口径**：n / seed / 任务数建议值（8–12 run 量级，冻结时定稿）；指标 = 分类犯病率、假完成宣称率、法官检出率、健康误杀率；判定口径与"犯病"的操作定义逐类写死。
- **预算封顶**：run 数 / token 上限；**熔断**：法官在 bait 任务上失效（误杀健康或漏检注入病）→ 停 M4 回 M3 修法官。
- 如实随档模板（n 小、单模型、任务面构造性等外推边界）。

### 步骤 2：跑批

真实 profile headless 跑批，复用 spike 跑批器纪律（spawn 流式落盘 / heartbeat / taskkill 杀进程树 / 硬异常熔停 / `--resume` 断点续跑，`tools/experiments/spike/run-groups.mjs`）；结果入 `tools/experiments/ve-bench/results/m4-*/`（rows.jsonl + 逐 run 留档）。Let It Go：bait 任务诱导模型自然犯病，判定只走治疗臂证据规则，禁止代码层关键词/正则偷判模型意图。

### 步骤 3：AI 病理报告

《H-VE-M4-病理画像报告》（`docs/plan/`）：per-model 病理画像首版（deepseek-v4-flash-0731 最爱犯哪类病、发生率、法官检出交叉表）；结构预留多模型对照；若稳定产生 falseCompletion 样本 → 那是 ADR-0018 §6(a)/(c) 证据，**另立 ADR 走重开评估程序，本计划不顺手重开**。

## 6. 熔断与砍序

- 任何工程需要碰 loop 层 / 运行期介入 / escalation 后端 → 立即停，回 ADR 复议（H-VE 计划 §9(d) 同纪律）。
- 契约字段无法投影到供给接口 → 先改契约文档（权威）再改码。
- M4 中法官失效 → 停 M4，回 M3 修法官，不续命（铁律 8）。
- 超支砍序：B3 砍 ③④ 类 bait 保 ①②（H-VE M1 先例）；B2 砍打包登记细节，保供给闭环与真实演示。
- 演示中 session log 格式与 `dsh-interface.md` 记录不符 → 以实测为准回写；M-D 演示降级为夹具 tool-log 并如实随档。

## 8. 如实随档（Not verified）要求

每批次交付物必须带 Not verified 小节：未验证的边界、构造者偏差风险、n/seed 限制、外推禁区。禁止把"机制存在且正确"写成"现网检出率"（效力报告 §6 的口径纪律延续）。
