## 1. 项目定位

Gungnir 是 DeepSeek Harness（DSH）的树外插件家族，最终形态是 DSH 的**自适应目标导引系统**：锁住版本化的人类意图（Lock the goal），按任务状态动态调整底层执行循环（Adapt the loop），用证据裁决每一次"完成"宣称（Prove the hit）。原生 `/goal` 解决"我要一直做这件事"；固定 ReAct 解决"怎么一步步做"。Gungnir 解决的是：

> **"现在的任务状态该用哪种控制算法来跑，以及你凭什么证明它正在把现实推向我要的目标？"**

核心研究对象是 **Adaptive Cognitive Scheduling**（重新思考版 §二）：给 Agent 一个认知调度器。简单确定任务、探索任务、执行任务、验证任务、恢复任务需要的控制算法完全不同，没有第一性原理要求它们都跑同一种 ReAct。

分层图（来自 idea 文档结论并经 ADR-0012 修订，全项目唯一分层真理）：

```text
┌─────────────────────────────────────────────┐
│ Gungnir GoalSpec / Goal Contract            │  Lock the goal：什么必须成真？
├─────────────────────────────────────────────┤
│ Gungnir Adaptive Loop Runtime               │  Adapt the loop：现在该怎么干活？
│ （一次性替换默认 agent-loop 的 meta-loop）   │
├─────────────────────────────────────────────┤
│ Gungnir Evidence / Verifier / Reconciler    │  Prove the hit：凭什么证明命中？
├─────────────────────────────────────────────┤
│ DSH Agent Contract / Session Log / Services │  稳定机制层（不改源码，driver 可配置替换）
├─────────────────────────────────────────────┤
│ Tools / LLM / Sandbox                       │  实际操作层
└─────────────────────────────────────────────┘
```

命名与发布策略（ADR-0001）：仓库 `dsh-gungnir`（吃 `dsh-` 搜索流量），品牌 **Gungnir**（脱离前缀独立存在，单词品牌派）。npm 包名 `dsh-gungnir`（unscoped，符合生态内 `dsh-better-sidebar` 等惯例）；loop 驱动包发布名候选 `dsh-gungnir-loop`（四阶段定）。

## 2. 战略主线（为什么是这个顺序）

三条硬结论，任何阶段不得违背：

1. **机制稳定，策略多变**（重新思考版 §五，ADR-0012）。必须稳定的：Agent contract、session identity、append-only ledger、tool safety、cancellation、persistence/replay、observability。允许激进变化的：context projection、model、reasoning budget、工具呈现与执行策略、branching、validation/retry/stop policy、planning depth、subagent topology、workflow strategy。旧判断"替换机制会击穿 append-only 脊柱"已被 DSH 架构证伪：loop 是执行层，session log 是事实层，换掉执行层照样忠实产出 durable events。
2. **证据层是 loop 的传感器与裁判**（初步结论，经一阶段兑现）。meta-controller 需要的全部切换信号（progress、error rate、verification debt、goal predicates）来自 Evidence + Verifier 层；loop 对照实验的成功与否也由它判定。一阶段生死假设已验证（20/20 一致、假验收 0），传感器就位，现在造调度器。
3. **先 spike 后完全体，打不过就回退**（重新思考版 §十七）。核心对照实验必须包含 Code/PTC 与 Workflow baseline——要证明的是 Gungnir 比 DSH 已拥有的 Code Mode + Workflow 还能多创造多少价值，只赢 Standard 不算赢。判定门跑批前预注册；打不过 Code/PTC 即回退方案 B（附录 A）。

另一条贯穿全程的工程铁律：**绝不修改 DSH 源码，绝不 fork DSH**。默认 agent-loop 经官方组合接缝一次性替换为 Gungnir Adaptive Loop Runtime；运行期切换的是 Loop Strategy，禁止物理热插拔（ADR-0012）。Goal、Ralph、Workflow 已经证明"看似不同的执行模式本来就是可替换 policy"；DSH 官方架构明示 agent loop 与其他部件一样可从配置替换——Gungnir 把这条接缝用到底。

## 4. 各阶段详述

### 4.1 一阶段：Gungnir Core——证据基石（Prove 支柱地基）

> **状态：已完成（2026-08-28）**。本节保留为执行期范围记录；实现偏差与执行中修复见《一阶段实施详细计划》卷首回写与 ADR-0006～0009。

**范围（来自初步结论的"第一刀"，严格执行）**：

- `/ultragoal <objective>` 命令 → GoalSpec（手写/直接给，**不做**自动苏格拉底澄清）。
- 每轮只 commit 一个 action，执行后从 `tools/result` 抓 evidence。
- 实现 2–3 类 Verifier：exit code（deterministic）、文件/artifact、LLM rubric（semantic）。
- 重点做破坏测试：改文件、杀进程、DSH 重启后能否从 event ledger 重建状态继续——这是 idea 文档自己也认为最有价值的测试。
- ledger schema 设计时预留 `loop/state`、`loop/transition` 两类事件——ADR-0012 后于二阶段接入，预留决定被证明正确。

**掉头后的重定位**：一阶段资产是"Prove the hit"支柱的地基，也是 Adaptive Loop 的传感器（切换信号源）与对照实验的裁判（成败判定器）。先打证据这一仗的顺序决策（ADR-0002）被保留为正确决策；变的只是"后 Loop"的含义——从"loop 之上的控制平面"改为"替换 loop 实现"。

执行细节见《[一阶段实施详细计划](一阶段实施详细计划.md)》。

### 4.2 二阶段：Adaptive Loop Spike——替换默认 loop 的尖峰验证

**定位**（ADR-0012）：不要一上来重写完整 DSH loop。先用最小体量证明"Adaptive Loop 比 DSH 已有的 Code Mode + Workflow 多创造价值"，再投完全体。

**范围**：

1. **v0.1.2 适配三件套先行**（沿用 ADR-0011 登记，任何方向都绕不开）：③ 插件 patch 移除 storage 插入行恢复 boot；② wrapup 时序真实 profile 复核；① 工具 schema 补 `additionalProperties`。
2. **替换 seam 实证（OPEN-7）**：树外 loop 包如何经 bundles 层栈替换 `dsh-agent-loop`（官方文档承诺可从配置替换，源码树 `docs/architecture.md:11,59`、`docs/capability-seams.md:507`、`apps/cli/composition.md:270`）；替代 driver 对 agent 生命周期、turn/step 边界、工具调度、teardown 职责的完整承担清单。
3. **AdaptiveLoopAgent v0**：实现 Agent contract 的稳定 driver，session 生命周期单实例；三模式 FAST / EXECUTE / VERIFY（定义见详细计划 §3）；**确定性 router，不用 LLM router**；最小 transition budget 防振荡。
4. **loop 事件落账**：`loop/mode-selected`、`loop/transition` 等进 Gungnir ledger（ADR-0005 预留命名空间放开），可冷重建、可复盘成模式轨迹图。
5. **四组对照实验**：同一批任务跑 DSH Standard / DSH Code-PTC / DSH Workflow / Gungnir AdaptiveLoop。指标：task success、input/output tokens、LLM calls、tool calls、LLM round trips、wall-clock latency、cache hit、validation failures、instruction violations、loop repetitions、recovery count。

**明确不做**：LLM router / meta-model；DELIBERATE / RECOVER / FINALIZE 完全体；五级 Verifier 补全、GoalSpec Compiler、WAITING_EXTERNAL（原 Proof-Carrying 内容并入三阶段）；多 goal；任何 DSH 源码修改。

**继续/熔断门**（实验门槛建议值，非已验证事实；跑批前预注册）：task success 不下降，且满足 input token ↓≥20% / LLM round-trip ↓≥25% / latency ↓≥15% / 重复无效步骤 ↓≥30% 之中至少两项。

**熔断条件**：(a) 连 Code/PTC baseline 都打不过 → 暂停替换路线，回退方案 B（附录 A）；(b) 替换 seam 实证发现须修改 DSH 源码才可达 → 回退方案 B，写 ADR 复盘；(c) 事件语义破坏（resume/fork 失败、turn/step 事件语义漂移）→ 红线，直接停，修到语义对齐才准继续。

执行细节见《[二阶段实施详细计划](二阶段实施详细计划.md)》。

### 4.3 三阶段：Evidence-Guided Control Plane——Passive Prove 主线 + Passive Proof Spike

**前提（2026-08-29 三修订，ADR-0017）**：二阶段 spike 冻结门 FAIL 已按预注册熔断执行；post-mortem（《二阶段-postmortem》）用逐会话剖析把归因从笼统的"loop 开销"修正为成本三分解——Verification Tax（干净任务实测 ≈0 额外往返，必要）、Protocol Tax（协议仪式实测 2–3×，该砍）、Bug Amplifier（t2 会话 65% 的 wall-clock，必须修）。三阶段重定义为两线：**P0 = Passive Prove 主线**（现役形态的 passive 化，跑默认 driver，独立启动）；**P1 = Passive Proof Spike**（运行期控制面唯一幸存假设的检验，执行基准《[三阶段-Passive-Proof-Spike计划](三阶段-Passive-Proof-Spike计划.md)》）。

**Passive Prove 主线**（P0）：在一阶段插件形态之上做四件事：关掉协议指令注入（主 Agent 不参与 Gungnir 协议）；wrapup seam 挂确定性验证钩子（L1/L2/L3，L4 禁用至独立 benchmark 证成）；裁决改造为 Minimal Actionable Feedback（AP-6）；GoalSpec 改为渐进式形式化（L0 隐式 / L1 轻量 / L2 完整，AP-3）。五级 Verifier 阶梯补全、spec 变更语义、evidence-derived progress metrics、GOAL_REVALIDATION 增强、WAITING_EXTERNAL 等原八项沿此形态继续，细则见《[三阶段实施详细计划](三阶段实施详细计划.md)》（待 passive 化修订）。

**Passive Proof Spike**（P1）：唯一核心问题——被动控制面能否拿到接近外部法官的可靠性收益，同时让正常任务成本接近原生 DSH？五组对照：C0 Native / C1 External Judge（上限参考）/ C2a（仅通用不变量判据，测下限）/ C2b（加一次性轻量判据捕获，测中间态）/ C3 Active v0（负对照）。任务面把诚实任务与四类对抗任务（False Claim / Misleading Test / Constraint Trap / Incomplete Goal）并入同一 spike；判据来源三层（S1 通用不变量 / S2 一次性捕获 / S3 外部供给）的选取是第一预注册问题。判定门：正常任务 token ≤ +5–10%、额外 LLM 往返 ≈ 0；对抗任务 False Completion 显著下降；Intervention Precision/Recall 达标（跑批前预注册冻结）。

**冻存资产**（P2）：`@gungnir/agent-loop`（Adaptive Loop Runtime）、Branch Search、Recovery 等重型策略冻存为 escalation 后端——默认不加载、不继续 patch；"被罕见调用即回本"的设想是未测假设，不计入当前价值主张。Adaptive Runtime 完全体（重新思考版 §八/§九 的六模式策略集与 meta-controller）随此一并存档。

**验证实验**：Prove 线 = verdict 可信度实验（预注册先行，沿用三阶段设计稿 B8 框架并按 passive 形态修订）；控制面线 = Passive Proof Spike 对照实验（判定门跑批前预注册，见 spike 计划）。

**熔断条件**：spike 判定门 FAIL → **最终退出线**：运行期控制面形态整体复盘，Gungnir 收缩为离线 Verifier / 评估资产，四阶段按此形态发布（ADR-0017）。大量 goal 建不起稳定 success criteria → Contract-first 降级为 objective + evidence-only（保 Verifier 资产）。初始计划原样执行率极低且 replan 不收敛 → 停止 plan projection 投资，转纯 reactive reconcile。

### 4.4 四阶段：Open Gungnir——生态与发布

1. **v1.0 发布**：`dsh-gungnir` + `dsh-gungnir-loop` npm 包、README（第一句 slogan + 一句话定义，EN/ZH 双语）、架构文档、快速上手（`dsh plugin --profile <name> add …`）。

5. **社区**：DSH Plugin Registry 提交、对 upstream 的反馈/PR（勘察中发现的文档缺口；loop 替换 seam 的实测经验是上游"deferred until such a consumer exists"领域的首个消费者样本）。

## 5. 跨阶段工程规范

- **仓库形态演进**：pnpm workspace。包划分：`@gungnir/core`（纯域函数 + loop 路由规则）、`dsh-gungnir`（Prove 层插件）、`@gungnir/agent-loop`（二阶段新增，Adaptive Loop Runtime 驱动包，发布名候选 `dsh-gungnir-loop`）；后续 verifier/tooling 按需拆包。
- **DSH 版本跟踪**：peerDependencies 锁实测过的版本。当前基线 = **v0.1.2-alpha.1 源码构建**（ADR-0011，2026-08-28 起；全局 `dsh` 经 `tools/dsh-shim/` 转发到源码树构建产物，npm 未发布）：三处适配点（③ v0.1.2 base 自带 storage 与插件 patch 冲突〔boot 实证〕；② tool-goal complete/blocked 改 wrapup 不再硬停 turn；① defineTool 强制 `additionalProperties`）并入二阶段 M0 落地，随后跑 `docs/context/dsh-interface.md` §14 接缝回归清单与破坏矩阵。上游 alpha 演进或正式版发布时再复审。
- **测试纪律**：域核心（schema/fold/状态机/路由规则）纯函数全单测；DSH 集成走真实 profile（`dsh plugin --profile gungnir-dev add <local>` + headless 冒烟），不做离线 mock 联调；破坏测试是第一等公民（进程 kill、重启、环境漂移、策略振荡注入），进 CI 脚本。dev/实验 profile 统一 `DSH_TELEMETRY_DISABLED=1`。
- **文档义务**：每个包 README 含 Contract 与 Known Limitations（对齐 DSH 上游文风）；架构级决策先进 `docs/context/decisions.md` 再写码；每个工作块结束更新 `docs/context/state.md`；实测或源码勘察推翻计划假设时，同批回写对应计划文档（本文件 v1.1 与 v2.0 均为该规则的产物）。
- **上下文纪律**：所有会话（人或 agent）按 `docs/context/README.md` 的渐进式披露路径取上下文，禁止一次性全量阅读仓库。

## 附录 A：方案 B——Seam-only 控制平面（降级形态存档）

> ADR-0012 的熔断退路：仅当二阶段 spike 触发熔断（打不过 Code/PTC，或 seam 须改源码）时启用。本附录是掉头前三阶段的压缩存档，启用时按当时基线重新勘察接缝。

**形态**：完全不替换 agent-loop，经 `agent/pre-step`、`agent/request`、`agent/request-error`、`tools/pre-execute`、`tools/post-execute`、`agent/turn-stopping`、workflow、Code Mode、subagent 等 seam 实现控制。

1. **LoopPolicyVector 取代 Loop Mode**：Mode 是涌现状态，不是一级实体。策略维度（暂定七轴）：cognition（reactive/deliberate/explorative）、orchestration（direct/subagent/workflow/fresh-agent）、continuation（natural-stop/goal-round/forced-continue）、verification（none/self-check/independent）、context（same-session/compact/fresh）、model（cheap/balanced/strong）、action（inspect/modify/validate/recover）。
2. **Loop State Estimator**：从 session/tool 事件流估计 ambiguity、progress、stagnation、failure、risk、contextPressure、parallelizability、verificationDebt、budget。
3. **Transition Guard**：minimum dwell steps、transition cooldown、evidence threshold、switching cost、failure counter、fallback state；event-driven，只有模糊转换才请 meta-model。
4. **Propose / Authorize 分离**：Agent propose（`propose_loop_transition(...)`），Harness 依 evidence authorize；sandbox/approval authority 归原 owner。
5. **Durable events**：`loop/state`、`loop/transition` 进 ledger（同一预留命名空间）。
6. **策略作用面**：只用 DSH 已有扩展点——prompt policy、tool execution gate、model route（installModelSelection / agent/request；v0.1.2 的 subagent `agentOptions`）、continuation（goal round 控制）、verifier 触发。
7. **受限组合**：L5 human 仅 root agent 可调，orchestration=subagent/fresh-agent 时须先回 root 上下文问人。

**已知天花板**（重新思考版 §十二）：只能影响 loop 的 decision，不能拥有 loop 的 topology；自定义 step topology、branch search、深度 context projection 能力显著弱于替换路线。长期警惕"用越来越复杂的插件模拟另一个 agent-loop"。
