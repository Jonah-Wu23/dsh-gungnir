# Gungnir 全阶段实施计划

> **Gungnir is a durable, evidence-driven goal reconciliation runtime that continuously drives observed reality toward a versioned human intent.**
>
> Tagline：**Declare it. Gungnir never misses.**（言出必中。）

- 文档定位：全局路线图。回答"每个阶段做什么、为什么这个顺序、何时触发熔断"。具体到本周做什么的执行细节见《[一阶段实施详细计划](一阶段实施详细计划.md)》。
- 依据来源：`docs/idea/` 三份文档（Agentloop 自动调整、UltraGoal、初步结论）全文，以及对已安装 `@deepseek-ai/dsh@0.1.1-rc.2` 的实测勘察（接口事实见 `docs/context/dsh-interface.md`）。
- 状态：v1.0（2026-08-28 起草）。本计划受 `docs/context/decisions.md` 中的 ADR 约束，重大变更须先落 ADR。

## 1. 项目定位

Gungnir 是 DeepSeek Harness（DSH）的树外插件家族，最终形态是 DSH 原生 `/goal` 之上的**第二代 Goal Runtime**，外加一个位于其上的**自适应循环控制平面**。原生 `/goal` 解决的是"我要一直做这件事"；Gungnir 解决的是：

> **"你凭什么证明，你一直做的事情正在把现实推向我真正要的目标？"**

四层架构（来自 idea 文档结论，全项目唯一分层真理）：

```text
┌─────────────────────────────────────────────┐
│ Gungnir GoalSpec（三、四阶段：Goal Contract）│  What must become true?
├─────────────────────────────────────────────┤
│ Gungnir Reconciler + Adaptive Loop Plane    │  How should I work NOW?
├─────────────────────────────────────────────┤
│ DSH Agent / Goal / Workflow / Subagent      │  Execute the chosen policy
├─────────────────────────────────────────────┤
│ Tools / LLM / Sandbox                       │  Perform actual operations
└─────────────────────────────────────────────┘
```

命名与发布策略（ADR-0001）：仓库 `dsh-gungnir`（吃 `dsh-` 搜索流量），品牌 **Gungnir**（脱离前缀独立存在，单词品牌派）。npm 包名 `dsh-gungnir`（unscoped，符合生态内 `dsh-better-sidebar` 等惯例）。

## 2. 战略主线（为什么是这个顺序）

三条来自 idea 文档的硬结论，任何阶段不得违背：

1. **依赖是单向的**（初步结论）：Loop 控制平面需要的全部切换信号——progress_delta、error_rate、verification_debt、evidence threshold、goal predicates——正是 UltraGoal 的核心资产（Evidence + Verifier 阶梯）。先做 Loop 就是盲切：控制器没有传感器。
2. **两个项目共用一个生死假设**："能否用证据驱动的方式，在开放世界任务上可信地判定进展"。这个假设立住，它既是 UltraGoal 的护城河（Proof-Carrying Goal Execution），也自动成为 Loop 层的信号源；这个假设倒了，两个项目都死。先打这一仗，信息杠杆最大。
3. **Loop 的验证实验本身依赖 UltraGoal**：fixed vs adaptive 对比实验的"成功率、verification 覆盖率"指标需要 Verifier 层来判定，否则只能人工看 20 个任务，不可信不可复现。

因此：**先 Reconciler（一、二阶段），后 Loop Plane（三阶段），最后生态化（四阶段）**。每阶段设熔断条件，触发即停、转向或降级，不允许"再加一个 patch 试试"。

另一条贯穿全程的工程铁律：**绝不修改 DSH 的 `agent-loop`，绝不 fork DSH 核心**。DSH 官方立场明确——一切新行为做成插件；Goal、Ralph、Workflow、Plan Mode 已经分别证明了"看似不同的 Loop 本来就应该是独立 policy plugins"。Gungnir 不重新发明 `/goal + loop + workflow`，只新增 **GoalSpec / Evidence / Verifier / Reconciler** 这一层（后期再加 Loop Policy 层）。

## 3. 阶段总览

| 阶段 | 代号 | 一句话目标 | 核心交付 | 关键验证 | 熔断条件 |
|---|---|---|---|---|---|
| 一阶段 | **Gungnir Core** | 证据驱动 Reconciler 最小骨架跑通 | `/ultragoal` 命令、event-sourced ledger、证据捕获、3 类 Verifier、reconcile 闭环 | 破坏测试：改文件/杀进程/DSH 重启后能从 ledger 重建并继续；20 个混合任务上 verdict 与人工判定的一致率 | 证据驱动判定在 20 任务上一致率不可接受（详见 §4.1） |

## 4. 各阶段详述

### 4.1 一阶段：Gungnir Core——Reconciler 最小骨架

**范围（来自初步结论的"第一刀"，严格执行）**：

- `/ultragoal <objective>` 命令 → GoalSpec（手写/直接给，**不做**自动苏格拉底澄清）。
- 每轮只 commit 一个 action，执行后从 `tools/result` 抓 evidence。
- 实现 2–3 类 Verifier：exit code（deterministic）、文件/artifact、LLM rubric（semantic）。
- 重点做破坏测试：改文件、杀进程、DSH 重启后能否从 event ledger 重建状态继续——这是 idea 文档自己也认为最有价值的测试。
- ledger schema 设计时预留 `loop/state`、`loop/transition` 两类事件，后续接 Loop 层不返工。

**明确不做**：苏格拉底澄清系统、Contract VM、完整五级 Verifier、plan versioning、多 goal、跨 session goal。

**生死实验**：20 个 coding/research 混合任务。测三件事——(a) verifier verdict 与人工 ground truth 的一致率；(b) 破坏注入后 resume 成功率；(c) claim≠evidence 分离是否真实成立（模型谎报时系统能否不被骗）。

**熔断条件**：如果 (a) 一致率低到无法支撑 Phase 3 的信号需求（经验阈值：可判定任务上 < 70%，或错误判定中"假验收"占比不可忽略），说明"证据驱动进展判定"这一共享生死假设不成立。此时停下，写复盘，方向降级为"半自动 goal 助手"（Verifier 只做展示不做裁决）或放弃，不做无依据的续命。

执行细节见《[一阶段实施详细计划](一阶段实施详细计划.md)》。

### 4.2 二阶段：Proof-Carrying——证据与契约完全体

把一阶段骨架升级为 idea 文档定义的护城河。按优先级：

1. **五级 Verifier 阶梯补全**（UltraGoal 文档 §16，原则：能用 1 绝不用 4）：
   - L1 Deterministic：exit code、测试、JSON predicate、文件 hash、HTTP status（一阶段已有雏形）。
   - L2 Artifact：文件存在、字段存在、diff、schema、编译产物（一阶段已有雏形）。
   - L3 External-state：重新查询网页/API/数据库确认现实状态（新增）。
   - L4 Semantic：LLM/rubric（一阶段已有雏形，本阶段强化 rubric 管理）。
   - L5 Human：无法机器证明的 acceptance criterion 显式交回用户（新增，接入 `tool-ask-user`）。
   - Verifier 选择器：success criterion 声明 verifier kind，系统强制沿阶梯取最高可信级。
2. **GoalSpec Compiler（轻量版）**：澄清问题只问"会改变下一步/Verifier/风险/成本"的决策相关不确定点（UltraGoal 文档视角 C），不是每次十个问题。产出 versioned GoalSpec：objective、success criteria、constraints、non-goals、assumptions、user preferences、invariants。
3. **Plan invalidation 与 replanning**：plan 只是 rolling-horizon projection（每轮重新生成、只 commit 一个）；显式 INVALIDATE/REPLAN 事件，留痕"为什么改"。
4. **Progress metrics**：acceptance criteria satisfied m/n、blocking unknowns、verified artifacts、critical uncertainty——不依赖"模型觉得自己有进展"。
5. **熔断器**：连续 N round 无 GoalStatus 改善、重复相同 action、超预算、Verifier 长期 INCONCLUSIVE → 进入 BLOCKED / NEEDS_HUMAN，停止烧 token。
6. **WAITING_EXTERNAL**：区分"被动等待外部事件"与"需要继续推理"，解决原生 goal-round 的 idle 空转问题（UltraGoal 文档引用的 discussion #4664）。
7. **GOAL_REVALIDATION**：完成前从头重查所有 goal-level acceptance criteria、constraints、invariants。软件语境=回归测试，研究语境=结论交叉验证，申请语境=材料总审计。

**验证**：50–100 个真实任务，统计：初始计划原样执行率（Contract VM 熔断指标的反向引用）、replan 收敛性、verdict 可信度分层（L1–L5 各自的 precision）。

**熔断条件**：若大量 goal 连稳定 success criteria 都建立不起来 → Contract-first 路线价值存疑，回退为 objective + evidence-only 模式（弱化 spec，保住 verifier 资产）。

### 4.3 三阶段：Gungnir Steering——自适应循环控制平面（方案 A：Loop OS）

**定位**（Agentloop 文档结论）：不改 `agent-loop` 的自适应控制平面。Reconciler 本身就是一个固定策略的 meta-loop（observe → plan → commit one action → verify → reconcile）；本阶段把它变成"执行策略可自适应"。

**核心机制**：

1. **LoopPolicyVector 取代 Loop Mode**——Mode 是涌现状态，不是一级实体。策略维度（暂定七轴）：cognition（reactive/deliberate/explorative）、orchestration（direct/subagent/workflow/fresh-agent）、continuation（natural-stop/goal-round/forced-continue）、verification（none/self-check/independent）、context（same-session/compact/fresh）、model（cheap/balanced/strong）、action（inspect/modify/validate/recover）。
2. **Loop State Estimator**：从 session/tool 事件流估计 ambiguity、progress、stagnation、failure、risk、contextPressure、parallelizability、verificationDebt、budget。信号源即一、二阶段的 Evidence 层——这正是"先 UltraGoal 后 Loop"的兑现。
3. **Transition Guard**：TCP 拥塞控制式防振荡——minimum dwell steps、transition cooldown、evidence threshold、switching cost、failure counter、fallback state。**event-driven，不是每 step 都调 LLM**：简单信号规则裁决，只有真正模糊的 transition 才请 meta-model。
4. **Propose / Authorize 分离**（机制设计视角）：Agent = propose（`propose_loop_transition(...)`），Harness = authorize（依据测试结果、文件 diff、tool outcome、unresolved todo、goal predicates、validator 裁决），Environment = provide evidence。模型有建议权，Harness 有裁决权；sandbox/approval 安全 authority 仍归原 owner。
5. **Durable events**：`loop/state`、`loop/transition` 进 ledger（schema 一阶段已预留），每次转换记录 from/to/reason/evidence/trigger/turn/step。继承 DSH 铁律：模型可见的必须能从 session log 重构。
6. **策略作用面**：只用 DSH 已有的扩展点——prompt policy（system-prompt/assemble、pre-step 注入）、tool execution gate（tools/pre-execute）、model route（agent/request waterfall / installModelSelection）、continuation（goal round 控制）、verifier 触发。

**验证实验**（Agentloop 文档 48–72h 实验的完整版）：≥20 个 coding/research 混合任务，fixed loop vs adaptive loop 对照，指标全部由 Gungnir 自身 Verifier 层判定（这是一阶段投资的回报）：成功率、tool calls、token、错误重复次数、完成前 verification 覆盖率、transition 次数、振荡指标（transition/round 比）。

**熔断条件**：自适应无统计显著收益，或 hysteresis 调不到稳定（振荡不可控）→ 冻结在固定策略 Reconciler，把 Estimator 降级为纯观测面板（仍有价值：成本仪表盘）。**方案 B（Loop VM）默认不做**——仅当三阶段数据显示大量高价值任务需要改变 Turn/Step 拓扑本身（谁先执行、哪里 barrier、哪里递归 fork/merge），即 Loop OS 熔断且原因明确指向"语法而非策略"时，才按 Agentloop 文档 §十 的 4-primitive prototype（MODEL/DELEGATE/VERIFY/CONTINUE + IF/GOTO/STOP）单独立项验证。

### 4.4 四阶段：Open Gungnir——生态与发布

1. **v1.0 发布**：`dsh-gungnir` npm 包、README（第一句 tagline + 一句话定义）、架构文档、快速上手（`dsh plugin --profile <name> add dsh-gungnir`）。
2. **文档与 demo**：README（EN/ZH 双语，对齐 DSH 生态惯例）、一个 end-to-end demo 任务（带破坏注入的恢复演示）、stage report 系列。
3. **UI cards**（可选）：对齐 `dsh-client-ui-*` 模式，为 GoalSpec/verdict/transition 提供渲染卡片。
4. **Skills**（可选）：通过 `ctx.skills.registerProvider` 提供内置 skill（如 "evidence-first completion"）。
5. **社区**：DSH Plugin Registry 提交、对 upstream 的反馈/PR（勘察中发现的文档缺口）。

## 5. 跨阶段工程规范

- **仓库形态演进**：pnpm workspace。一阶段两个包（`@gungnir/core` 纯域函数 + `@gungnir/dsh-plugin` 适配层），后续 verifier/tooling 按需拆包；发布名统一 `dsh-gungnir`（或按拆包策略 `dsh-gungnir-*`，四阶段定）。
- **DSH 版本跟踪**：锁 `0.1.1-rc.2` 起步，peerDependencies 对齐；每次 DSH 升级先跑 `docs/context/dsh-interface.md` 中的接缝回归清单再合并。
- **测试纪律**：域核心（schema/fold/状态机）纯函数全单测；DSH 集成走真实 profile（`dsh plugin --profile gungnir-dev add <local>` + headless 冒烟），不做离线 mock 联调；破坏测试是第一等公民，进 CI 脚本。
- **文档义务**：每个包 README 含 Contract 与 Known Limitations（对齐 DSH 上游文风）；架构级决策先进 `docs/context/decisions.md` 再写码；每个工作块结束更新 `docs/context/state.md`。
- **上下文纪律**：所有会话（人或 agent）按 `docs/context/README.md` 的渐进式披露路径取上下文，禁止一次性全量阅读仓库。

## 6. 熔断与转向总表

| 触发阶段 | 条件 | 动作 |
|---|---|---|
| 一阶段 | 20 任务 verdict 一致率不可接受 | 停止；复盘"证据驱动进展判定"假设；降级或终止 |
| 二阶段 | goal 连稳定 success criteria 都建不起来 | Contract-first 降级为 objective + evidence-only |
| 二阶段 | 初始计划原样执行率极低且 replan 不收敛 | 停止 plan projection 投资，转纯 reactive reconcile |
| 三阶段 | 自适应无显著收益 / 振荡不可控 | 冻结固定策略；Estimator 降级为观测面板 |
| 三阶段 | Loop OS 熔断且原因=需要改拓扑语法 | 才允许立项 Loop VM prototype（4 primitive，48–72h 验证） |
| 任意 | 出现"改 agent-loop 能更快"的诱惑 | 拒绝。写 ADR 说明为什么用插件实现，或放弃该特性 |

## 7. 风险登记册（跨阶段）

| 风险 | 影响 | 缓解 |
|---|---|---|
| DSH 处于 rc 期，API 可能变动 | 接缝断裂 | peerDep 锁版本；接缝回归清单；每次升级先跑冒烟 |
| `agent/pre-step` waterfall 顺序受插件加载顺序影响 | 与 goal-round-driver 的消息改写互相干扰 | M0 spike 实测顺序；必要时用 `Agent.inject()` 替代改写 |
| session compaction 与 ledger 事件交互未验证 | 事件被裁导致状态不可重建 | M0 spike 显式测试 compact 后 replay |
| LLM rubric verifier 成本与稳定性 | 二阶段成本失控 | 阶梯原则强制兜底；rubric 结果缓存；预算进熔断器 |
| 独立开发者带宽 | 阶段拖长、上下文漂移 | 时间盒 + stage report + docs/context 活文档机制 |
| "又一个 Harness" 陷阱（重造 workflow/scheduler/recovery） | 范围爆炸 | AGENTS.md 铁律：只新增 GoalSpec/Evidence/Verifier/Reconciler(+LoopPolicy) 层 |
