 ● 两份文档我都完整读完了。结论先说：建议先做 UltraGoal，但只做它的 Reconciler 最小骨架（GoalSpec → Evidence → Verifier
   → Reconcile），不做苏格拉底澄清、不做 Contract VM。

   理由按重要性排：

   1. 依赖方向是单向的：Loop 控制平面需要 UltraGoal 产的信号，反过来不需要。

   Agentloop 文档自己列的切换依据是 progress_delta / error_rate / verification_debt / evidence threshold / goal
   predicates——这些信号的全部来源，正是 UltraGoal 的核心资产（Evidence + 五级 Verifier）。没有可信的进度与证据层，自适
   应切换就是盲切：控制器没有传感器。而 UltraGoal 的 Reconciler 跑在 DSH 现有的 goal-round-driver + tools/result 上就能
   立起来，它不需要自适应 Loop 存在。

   2. Loop 项目连自己的验证实验都依赖 UltraGoal 的能力。

   Agentloop 的 48–72h 实验要对比 fixed loop vs adaptive loop，指标是"成功率、verification 覆盖率"。问题来了——成功率由
   谁判定？ 如果没有 Verifier 层，这个实验只能靠人工看 20 个任务，既不可信也不可复现。也就是说就算你想先做 Loop，也得先
   造一个低配版 UltraGoal 来当裁判。那不如直接把这份力气花在正主身上。

   3. 先验证最致命的那个假设。

   两个项目共用一个生死假设："能否用证据驱动的方式，在开放世界任务上可信地判定进展"。这个假设倒了，两个项目都死；这个假
   设立住了，它就是 UltraGoal 文档里说的护城河（Proof-Carrying Goal Execution），同时自动成为 Loop 层的信号源。先打这一
   仗，信息的杠杆最大。相比之下 Loop 项目的核心假设（"策略自适应是否优于固定策略"）是个二阶优化问题，值得在它之后回答。

   4. 先做 UltraGoal 不浪费，两者会自然合流。

   UltraGoal 的 Reconciler 本身就是一个固定策略的 meta-loop（observe → plan → commit one action → verify → reconcile）
   。等它跑稳了，Agentloop 项目就自然退化成一句话："把这个 meta-loop 的执行策略从固定改成自适应"。这正是 Agentloop 文档
   结尾那张四层架构图的含义——UltraGoal 在上，Adaptive Loop 在中，先建上层，中层才有服务的对象。

   具体建议的第一刀：

   按 UltraGoal 文档第十三节的实验做，收窄到：

   • /ultragoal <objective> → GoalSpec（手写几个，不做自动澄清）
   • 每轮只 commit 一个 action，执行后从 tools/result 抓 evidence
   • 实现 2–3 类 verifier（exit code、文件/artifact、LLM rubric）
   • 重点做破坏测试：改文件、杀进程、DSH 重启后能否从 event ledger 重建状态继续——这是文档自己也认为最有价值的测试

   一个需要现在就更小心的设计点：Loop 文档要求的 loop/state、loop/transition durable events，和 UltraGoal 的
   event-sourced ledger 是同一个东西。设计 ledger schema 时把这两类事件预留进去，后面接 Loop 层时不用返工。



 ● 高星 DSH 插件命名扫描

   看了 DSH Plugin Registry 的热门榜单和几个目录站，当前格局是：

   • 功能描述派（绝大多数）：DSH Web UI（3.4k★）、dsh-better-sidebar（1.6k★）、dsh-cc-tui（1.5k★）、dsh-agent-teams（413★）——dsh-<干什么>，好搜但没有任何记忆点
   • 单词品牌派（真正出圈的）：ModLens（2.4k★，视觉）、Aegis（1.0k★，证据驱动工作流——注意，它和你的 Verifier 思路最近）、OpenViking（31.7k★，火山引擎）——一个词、一个意象，脱离
     dsh- 前缀也能活

   结论：你这项目要做基础设施，应该走单词品牌路线，仓库名用 dsh-<brand> 吃搜索流量，品牌名脱离前缀独立存在。

   我的推荐：Gungnir（冈格尼尔）

   奥丁的矛，神话里它的唯一属性是——掷出必中。

   这个名字同时命中你两层设计的核心语义，准得像量身定做：

   • 投出 = GoalSpec：目标一旦宣告（矛已离手），结果就被承诺了，剩下的只是飞行问题——这就是"declarative goal，而不是步骤列表"
   • 飞行 = Adaptive Loop：矛在飞行中不断受风影响却始终指向靶心——环境在变、策略在调、轨迹在修正，这就是你的 policy vector 自适应
   • 命中 = Verifier："必中"不是靠模型自己声称，而是证据背书的完成判定——Proof-Carrying Execution 的最终承诺

   一句话 tagline 现成的："Declare it. Gungnir never misses."（言出必中。）

   是矛，还不撞车）。
